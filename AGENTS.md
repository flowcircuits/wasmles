# AGENTS.md

## What this is

`@flowcircuits/wasmles` — a small WebAssembly linear equation solver written in Rust. Rust does the math (via `nalgebra`), `wasm-bindgen` exposes it to JS, and `wasm-pack` builds browser + node bundles. That's the whole project.

## Communication Style

- Be concise; get right to the code.
- Challenge and override when you think I'm wrong.
- Write production-ready code. Be thorough — don't get lazy or leave dangling threads.

## Engineering Practices

Our number one rule is **SIMPLE**. This is a single-purpose library — keep it that way.

- No new abstractions, layers, or "frameworks." Inline one-off logic.
- Don't add defensive code for cases that can't happen; trust internal callers.
- Validate only at the boundary — the `JsValue` coming in from JS (already done in `src/lib.rs`).
- Resist scope creep. If a change doesn't make solving linear equations faster, more correct, or easier to consume, push back.

## Layout

- `src/lib.rs` — the `#[wasm_bindgen]` entry points (`solveLinearEquations`, `solveLinearEquationClusters`). The JS boundary lives here.
- `src/linear_equations.rs` — equation types and solve logic.
- `src/matrix.rs` — matrix helpers.
- `tests/web.rs` — `wasm-bindgen-test` integration tests.
- `resources/` — hand-maintained `.d.ts` and `package.json` templates copied into `pkg/` by `postbuild.js` (the `VERSION` token is replaced with the real version).

The published artifact is `pkg/` (`pkg/browser` + `pkg/node`), generated by the build — never edit it by hand.

## Workflow

- Use `yarn` (not npm).
- Run `./setup.sh` once in a fresh checkout to install the toolchain and deps.

```bash
yarn build    # wasm-pack build for browser + node, then postbuild.js
yarn test     # cargo test
cargo test    # same tests, directly
```

- After changing Rust, run `cargo test`. Before declaring a change done, run `yarn build` to confirm the WASM bundles still build.
- Run `cargo fmt` to format Rust. JS/JSON formatting is 4-space indent (`.prettierrc`).

## Conventions

- The exported WASM functions are intentionally `camelCase` (matching the JS API), hence the `#[allow(non_snake_case)]`. Keep new exports consistent with the JS naming the consumer expects.
- If you add or rename an exported function, update the matching type declarations in `resources/` so the published package types stay correct.
- Bumping the published version: update `version` in `package.json` (and `Cargo.toml`); `postbuild.js` injects it into the package metadata.
- `Cargo.lock` is gitignored — this is published as a library.

## Publishing

CI handles it: pushes to `master` run build + test (`.github/workflows/test-and-build.yml`); creating a GitHub Release publishes `pkg/` to npm (`.github/workflows/publish.yml`). Don't `yarn publish` by hand.
